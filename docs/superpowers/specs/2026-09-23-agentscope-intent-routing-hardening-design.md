# AgentScope 意图路由与报表参数加固设计

## 背景

生产对话暴露了两类问题：

1. “全省中兴能耗报表”和“邵阳华为能耗报表”首次调用 `query_report` 时漏传地市或厂家，工具默认查询“全网-全网”，模型随后又重复查询才纠正。
2. 用户只问“邵阳有哪些厂家可以看”时，Agent 误生成完整报表；纠正性追问又误走小区解析，最终耗尽 ReAct 迭代次数。

现有主链路已使用 AgentScope 的 `Agent`、`Toolkit`、`MiddlewareBase`、`ToolChoice` 和 `ReActConfig`。本次不新增另一套智能体框架，也不新增“报表维度枚举工具”，而是收紧 AgentScope 现有组件的职责边界。

## 目标

- 明确报表请求首次就选择 `query_report`，且不能空参数查询错误范围。
- “有哪些厂家”继续使用现有 `query_business_data`，只返回厂家枚举结果。
- Middleware 只负责运行时约束和工具选择，不负责拼 SQL、查库或解析报表业务参数。
- 通用查询规划层正式支持“枚举唯一维度值”，不在 service 中写“邵阳+厂家”专用业务分支。
- 保留 AgentScope ReAct 对多步查询和图表链路的编排能力。

## 非目标

- 不新增独立意图分类模型或额外 LLM 调用。
- 不新增报表维度枚举工具。
- 不把地市、厂家、日期和 SQL 解析逻辑放入 Middleware。
- 不改变能耗报表指标口径、前推 7 天基线和 Markdown 格式。
- 不更改扩展、收缩、异常诊断和参数核查的业务阈值。

## 总体架构

```text
用户问题
  -> AgentScope Agent / ReAct
  -> GroundedToolChoiceMiddleware（证据门禁 + 高置信工具限定）
  -> 现有 Toolkit
       -> query_report（完整固定报表）
       -> query_business_data（字段、指标和维度值）
  -> DirectAnswerMiddleware 或工具专属总结 Prompt
  -> 用户结果
```

### AgentScope Middleware

Middleware 是 Agent 生命周期的拦截器，不是另一个业务 Agent。

- `GroundedToolChoiceMiddleware` 在本轮尚无工具证据时设置 AgentScope `ToolChoice`。
- 明确的完整能耗报表限定为 `query_report`。
- 明确的维度值枚举限定为 `query_business_data`。
- 其他业务请求仍使用现有工具集，由模型依据互斥工具描述选择。
- Middleware 不修改工具 arguments，不读数据库，不生成最终业务结论。

高置信规则只解决工具职责冲突，不在 Middleware 中枚举各种地市、厂家或字段。

### `query_report` Schema 和参数完整性

当前 `query_report` 的所有入参都可选，原生 function calling 可以合法地发出 `{}`，导致错误的“全网-全网”报表。

本次通过 JSON Schema 收紧必填参数，不在 Middleware 里补参数：

- `province`、`dist_name`、`county_name`、`prod_name`为必填字段。
- 用户未限定的维度由模型显式传入“全网”，工具不再因为空参数静默放大范围。
- `freq_band`、`site_type`、`area` 继续可选，未指定时使用现有“全网”默认值。
- 提示词和 Schema 字段说明明确“全省”对应 `dist_name=全网`，地市名规范化后传入 `dist_name`。
- Python 工具函数保留默认值，以兼容内部直接调用；AgentScope 对外 Schema 负责防止模型空调用。

### `query_business_data` 维度值查询

继续使用唯一通用数据查询工具。“邵阳有哪些厂家可以看”的结构化计划应表达为：

- 选择厂家字段 `prod_name`。
- 按 `prod_name` 分组，得到唯一维度值。
- 用 `dist_name=邵阳市` 过滤。
- 不查询能耗指标，不生成固定报表。

这个能力在通用规划层实现：

1. 规划 Prompt 明确“有哪些/可选值/唯一值”使用同一字段的 `select + group_by`。
2. 规划器结构化输出校验失败时，记录可定位的校验原因，并进行最多一次带校验反馈的修复重试。
3. 重试仍失败时返回明确错误，不改走小区解析或完整报表。
4. 维度枚举是通用查询内部的一种受控计划类型，不是新的 Agent 工具。它可对具有同一授权维度的多个候选表分别执行参数化查询，再对同名维度值做集合合并。
5. service 按计划类型执行通用查询，不保留“邵阳+厂家”专用 SQL、专用工具或专用返回格式。

对未指定 4G/5G 的厂家枚举，查询 `lte_report_day_collect` 和 `nr_report_day_collect` 中符合筛选条件的 `prod_name`，合并去重后返回；用户明确指定 4G 或 5G 时只查询对应来源。

## 实现收口

当前工作区中已有一版为快速修复案例而添加的实验性代码。正式实现首先收口这些变更：

- 删除消息适配层中的厂家专用正则和历史问题替换。
- 保留 Middleware 对高置信工具的 AgentScope `ToolChoice` 限定，但将判断收敛为少量工具职责边界。
- 将厂家枚举从专用 service 分支改造为通用维度值计划和通用合并执行。
- 保留已增加的失败日志详情，用于定位结构化规划校验错误。

### 多轮纠正和失败收口

- 保留“历史用户问题可用、历史助手回答隔离”的现有原则。
- 省略对象的纠正性追问由执行 Prompt 使用历史用户问题理解，消息适配层不写厂家专用重写规则。
- `query_business_data` 返回规划失败、需要澄清或零行时，总结 Prompt 必须回答当前状态，不得换用 `query_report` 或 `resolve_cell_cgi` 猜测。
- 完整报表的 `report_content` 仍由 `DirectAnswerMiddleware` 原样直出，避免二次模型改写。

## Prompt 调整

执行 Prompt 保持短且分层：

1. 先按用户最终产出区分“取数”与“专业报告/诊断”。
2. “有哪些厂家”是取数，不是报告。
3. 只有明确要求完整能耗报表时才用 `query_report`。
4. 工具失败后优先向用户说明失败或请求澄清，不为了完成循环而换用无关工具。

不把地市名单、厂家名单、SQL 模板或大量句式样例写入主 Prompt。

## 测试与验收

### 离线测试

- Middleware 测试：报表请求限定到 `query_report`，厂家枚举限定到 `query_business_data`，工具返回后解除首轮证据门禁。
- Schema 测试：`query_report` 的必填维度不允许空 function call。
- 规划器测试：维度枚举生成 `select + group_by`，一次校验修复后仍只能使用授权表和字段。
- 服务测试：厂家枚举走通用计划和通用输出，不走专用 service 分支。
- 消息测试：历史助手答案仍不进入 Agent context，消息层不做厂家专用重写。
- 全量回归：`PYTHONPATH=. .venv/bin/pytest -q`。

### 生产同款模型路由验收

评测样本至少覆盖：

1. `全省中兴能耗报表` -> `query_report(province=湖南省, dist_name=全网, county_name=全网, prod_name=中兴)`。
2. `邵阳华为能耗报表` -> `query_report(province=湖南省, dist_name=邵阳市, county_name=全网, prod_name=华为)`。
3. `邵阳有哪些厂家可以看` -> `query_business_data(question=原问题)`。
4. `我没问你，我只问有哪些` -> 复用最近的用户问题，重新调用 `query_business_data`。

路由评测只调用模型检查工具名和 arguments，可不访问业务库。数据结果验收需要目标环境数据库或最小脱敏样本。

## 生产数据要求

实现和离线测试不需要生产数据。端到端验证时，若无法连接目标数据库，只需导出最近 7 天、邵阳市、以下字段的脱敏结果：

- 表：`lte_report_day_collect`、`nr_report_day_collect`。
- 字段：`data_date`、`province`、`dist_name`、`county_name`、`prod_name`、`freq_band`、`site_type`、`area`。
- 可只保留去重后的维度组合，不需要能耗数值、小区名、CGI、基站号或用户数据。

只有在离线与生产同款模型路由测试通过后，才请求这份数据，避免用生产数据弥补代码设计缺陷。

## 回退

本次不修改数据库 Schema 或业务指标。若路由或参数行为退化，可单独回退 Middleware、Prompt、工具 Schema 和规划器修改，报表查询代码和数据库口径不受影响。

## 2026-10-29：地区节电空间查询的执行约束

“湘潭市的节电空间”暴露了批量工具漏传地市即查询全省的问题。此前的报表 Schema 约束未覆盖批量分析，原有回归也未验证模型漏参与错误地区最终生成的 SQL。

- 地区节电空间、节能潜力请求通过 AgentScope `ToolChoice` 限定到批量节电工具；明确 CGI 的节电空间请求限定到单小区工具。“节电空间报表”仍属于节电诊断。
- 新增 `app/services/query_scope.py`，在 Toolkit 中绑定本轮用户原话与历史用户问题。专业工具打开数据库会话之前校验地区，修正漏传、“全网”或错误地市，清理新地市查询中的旧区县。Middleware 不包含地名名单或 SQL。
- 范围约束覆盖批量节电、固定报表、异常与参数核查。湘潭县不转换成湘潭市；多地区、多厂家、批量分析范围缺失或工具无法表达区县条件时，返回澄清错误且不查询数据库。独立县级市无法确定层级时要求补充所属地市。
- 连续切换扩展档位沿最近的相关节电请求恢复范围与显式日期，不越过新的无关业务。纠正性追问以明确重新查询的目标为准。
- 当前轮工具证据与历史轮次隔离，上一轮成功结果不能触发本轮总结或解除取数门禁；要求重新查询也不能被当成只解释旧回答。
- 批量工具将“全网”等通配值转换为不筛选，固定报表保留查询汇总行的语义。Schema 保留内部调用兼容，防止范围扩大依靠执行校验，而非仅要求模型补齐必填参数。
- 工具元数据提供 `effective_input`，Dify 工具轨迹展示校正后实际传给业务函数的参数，报告仍由工具确定性生成。

默认 HTTP Agent 已自动绑定请求上下文。外部注入自定义 Toolkit 或独立构建 Toolkit 时，需要自行传入 `ToolRequestContext`。该规则层采用湖南地市全名、保守的简称边界与显式区县后缀；复杂地理语义、通用查询内部规划、数据库实际地名值仍需独立验收，不能据此认定全部意图识别问题已解决。

### 同日生产日志补充：末轮工具成功后结果丢失

用户提供的旧生产版本日志表明：服务启动完成；最新湘潭请求在工具执行前等待约158秒，业务工具约1.3秒完成并生成 Excel，随后 `exceed_max_iters` 使请求失败。另有独立的模型 `ReadTimeout`、完整维度日报重复记录及自助目录字段跳过；日志不足以确定前述长等待究竟来自模型思考、排队或多次无效返回。用户确认新修改尚未部署，内网环境通过复制文件、重启容器更新。

AgentScope 2.0.5 在每次推理和行动后都增加迭代计数。原报告直出要等待下一次 `ModelCallStartEvent` 才注入本地 `ChatResponse`；工具耗尽预算时根本没有下一次模型事件，因此成功报告仍被丢弃。修复后，`on_reply` 跟踪本次模型生成的整批 ToolCall ID，所有工具均已返回、结果成功且具有可直出的完整报告时，通过公共上下文和事件接口立即完成回复。失败、未完成批次、不同工具的混合结果和结构化输出不按此条件提前完成；不增加步数上限，也不将失败工具伪装成成功。

补充真实 Agent 回归：单步预算下工具成功、前三次只返回思考且第五步工具才成功，均须返回报告并正常完成。Dify 同时记录每次模型耗时、结束原因、token 数、文本/思考字符数和工具调用数，不记录思考正文；模型读取超时单独返回 `model_timeout`，不再笼统归为服务器内部错误。此改动没有证明上游超时已解决；日报重复记录仍需数据侧核查，不擅自相加或任选一行。

提供 `scripts/verify_production_patch.py`，在已有依赖的容器内执行文件 SHA-256、语法、依赖版本、范围和末轮结果的离线自检，不访问模型或数据库。补丁通过文件清单整体复制，包含新增 `app/services/query_scope.py`，不包含配置凭证、不修改依赖。离线自检通过不能替代真实模型与数据库验收。

离线验证使用真实 Agent→Toolkit→SQL构造→报告→Dify 链路，只替换模型、数据库读取与 Excel 导出边界。`PYTHONPATH=. .venv/bin/pytest tests -q` 验证项目回归；不要收集 `outputs` 中其他交付包的外部测试脚本。本地未配置内网模型地址与凭证，生产模型和真实数据库尚未验收，也未部署。已补充湘潭全名、简称、区县及节电空间报表的模型评测样本；目标环境可用 `RUN_AGENT_ROUTING_EVAL=1 PYTHONPATH=. .venv/bin/pytest tests/live/test_agent_routing.py -q` 执行首轮路由与原始参数评测。

### 同日三轮追问：统一任务状态与上下文预算

新的生产证据中，“湘潭市的节电空间”和“株洲市的呢？”均已成功；失败发生在第三轮“中等扩展”。该轮三次模型耗时约19.5、14.7、40.5秒，第二次原生工具调用被范围校验拒绝，第三次将 `<tool_call>` 当作正文返回。旧实现只向前寻找完整节电问题，遇到“株洲市的呢？”就停止，执行层未取得当前分析对象。不是数据库慢，也不是第二轮没有成功。

实际框架能力与项目接续要分开描述：已安装的 AgentScope 2.0.5 默认 ContextConfig.trigger_ratio=0.8，达到上下文阈值时可调用模型生成摘要；此前 HTTP 层每次新建 Agent，持久化仅保存最近20条问答原文，没有存取 AgentState.summary 或独立任务条件。这次约4363 tokens，远低于32768窗口的压缩阈值，触发摘要压缩并不能修复条件继承。

本轮改动：

- 在请求入口构建一次 ToolRequestContext，内部 TaskContext 保存工具、目标和实际条件。地区、厂家、日期、档位、分析目标使用同一条件合并器；更换城市清除旧区县，完整新任务重置条件，无关新业务阻断旧任务继承。旧会话只在入口重放用户条件，新会话读取结构化快照。助手正文和历史 XML 不用于恢复任务。
- 路由、工具输入校正、范围校验和执行共用该对象。明确的条件追问在同一个模型边界生成原生 ToolCallBlock，仍经过工具 Schema 校验与 Toolkit 执行；不为每种问句新增业务链路，不把文本 XML 转换成可执行调用。
- 成功工具返回实际生效参数快照，Dify 聚合后与 assistant 消息一同保存到现有 messages JSON 的 agent_context 字段，不增加数据库表。原始任务提问被20条历史截断后仍可从最新快照续接；显式 null 表示旧任务已清除。
- 模型历史输入有独立字符预算；预算内保留原文，超限保留近期对话并明确标记长消息截断。任务条件不从裁剪后的报告重建。数据库保存方式仍为最近20条，未实现永久全文归档、跨会话用户长期记忆或持久化框架语义摘要；不能把字符裁剪称作语义摘要。
- 模型边界缓冲并检查正文，跨分块的工具标签也不能发送给页面或保存为成功答案。模型累计等待默认60秒，包括重试与流正文等待；关闭 OpenAI SDK 内层重试，外层 AgentScope 重试仍受统一预算约束。已校验的范围澄清直接返回，不再调用模型解释拒绝。

离线验收包含真实三轮 Agent→Toolkit→Dify→持久化消息→下一轮恢复、条件组合与清除、长历史裁剪、单小区粒度切换、流式 XML 隔离、跨轮累计预算及 SDK 吞取消场景。生产模型兼容性、真实数据库结果和实际页面仍需目标环境复测。自检与补丁升级为 v2，保留前一版交付。

### v3：会话生命周期取代临时历史裁剪

用户确认上游验证身份并传入可信手机号。后续会话设计与实现以 [会话状态、用户隔离与框架接续](2026-10-29-session-state-lifecycle-design.md) 为准：conversation_id 保持全局唯一，按 user_id 校验归属；新增独立状态表保存原生 AgentState 的摘要、工作上下文及 Task；原始问答不再固定20条删除。v2 字符裁剪和重复补参/旧直出分支已移除，历史 agent_context 仅兼容读取，不再写入新问答。已有被截掉的本地历史不会自动恢复。保留范围防扩大、Schema 校验、原生工具调用、确定性报告直出及模型预算。v3 完整补丁新增 DDL 与身份参数说明，不能按 v2 的“只复制文件且不需要建表”方式部署。
