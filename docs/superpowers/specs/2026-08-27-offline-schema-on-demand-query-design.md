# 完全离线业务数据自服务工具设计

> **2026-08-31 范围变更：** RRU/AAU 资产表暂不对自助查询开放，当前目录为 12 张表。详见[暂停 RRU/AAU 数据自服务设计](2026-08-31-disable-rru-catalog-design.md)。

## 背景

现有 `query_metric`、`query_cell_metric` 和日报工具只能查询代码中预先登记的少量指标。业务人员还需要通过现有智能体入口，用自然语言查询已授权表的其他字段，并在可靠关系上组合最多三张表。

生产环境完全物理隔离，只有内部 OpenAI-compatible 大模型，没有 Embedding 模型。本阶段不引入外部数据平台、向量库、独立 Data Agent 或 MCP 服务，只在现有 AgentScope 工具体系中完善 `query_business_data`。

字段和指标是两种不同的数据能力：

- **物理字段**真实存在于数据库表中，可以直接查询；
- **计算指标**由固定来源字段和经过测试的代码公式产生，例如可读率、高耗电小区占比、低能效小区占比和平均休眠时长。

数据自服务负责可靠地取得和计算数据；跨日期比较、趋势判断、原因解释和建议仍由主智能体完成。

## 本阶段目标

- 保持现有聊天入口和 AgentScope 单智能体运行链路。
- 提供一个 `query_business_data(question, export_excel=False)` 工具。
- 使用显式表、字段、计算指标和关系白名单，不允许模型自由生成 SQL 或 JOIN。
- 字段目录展示英文名、中文名、业务说明、类型、别名和单位。
- 计算指标展示中文名、说明、来源字段、单位、粒度和固定计算函数。
- 单次最多查询三张表，只能沿审核关系组合。
- 没有 Embedding 时使用本地中文别名、英文名、连续包含和轻量模糊匹配召回候选。
- 返回结构化数据、来源、粒度、日期范围、默认条件和完整性信息，交由主智能体比较诊断。
- 保留可选 Excel 导出，但不由工具生成分析结论或完整报告。
- 继续使用独立只读数据库账号、查询超时、日期跨度和行数限制。

## 非目标

- 本阶段不提供 MCP、独立进程、独立端口、对外鉴权或远程调用协议。
- 不引入 Spring AI Alibaba DataAgent、StateGraph、Python 沙箱或多 Agent 编排。
- 不使用 Embedding、RAG、向量数据库或自动学习记忆。
- 不让模型编写任意 SQL、任意 Python、自由公式或自由关联键。
- 不在数据工具中判断异常原因、形成业务结论或给出优化建议。
- 不替换节电空间、参数核查、固定日报等已有专业工具。
- 第一阶段不允许计算指标作为过滤字段、分组字段或排序字段；主智能体可以对返回的有限数据做比较。

## 初学者视角：四层目录分别做什么

可以把查询过程理解成做菜：

1. **字段目录是原料表**：数据库里有什么，中文叫什么，业务含义是什么。
2. **指标目录是固定菜谱**：哪些原料按什么确定性公式计算成业务指标。
3. **关系目录是道路图**：哪些表可以连接、通过什么键连接、一行结果代表什么。
4. **查询执行器是厨师**：只按审核过的原料、菜谱和道路执行，不接受模型临时发明规则。

主智能体拿到结果后负责回答“这些数字说明什么”，数据工具只回答“这些数字是多少、从哪里来”。

## 总体架构

```text
用户自然语言
    ↓
AgentScope 主智能体
    ↓ query_business_data(question)
业务数据自服务工具
    ├─ 内存目录召回候选表、字段、指标和关系
    ├─ 内部大模型输出结构化 BusinessQueryPlan
    ├─ 程序校验白名单、关系、粒度和资源限制
    ├─ SQLAlchemy Core 构造参数化只读 SELECT
    ├─ 程序执行已注册的确定性指标函数
    └─ 返回结构化数据及可选 Excel
    ↓
AgentScope 主智能体比较、诊断和回答
```

主智能体和数据工具之间只保留一个工具边界。目录搜索、SQL 构造、指标计算不拆成额外模型工具。

## 授权表目录

第一批活跃目录包含当前代码已使用的 12 张表：

- 日明细：`lte_report_day_detail`、`nr_report_day_detail`
- 日汇总：`lte_report_day_collect`、`nr_report_day_collect`
- 工参：`lte_fix_prm`、`nr_fix_prm`
- 节电结果：`jd_cell_expansion_day`、`jd_cell_constriction_day`
- 过程证据：`jd_cell_detail_hour_nr`、`jd_cell_pre_hour_busy`、`jd_cell_around`
- 参数核查：`eng_check_result`

表策略明确记录实际 `schema_source`，不能假设所有表都位于同一个 PostgreSQL Schema。

## 显式字段白名单

每张授权表必须配置 `fields`，至少包含：

```yaml
fields:
  cgi:
    label: CGI
    description: 小区唯一标识，用于小区筛选和审核关系连接
    aliases: [小区标识, 小区号]
    unit: ""
```

字段来源按以下顺序核对：

1. 用户提供的数据字典和扩展、收缩 CSV；
2. 数据库字段 comment；
3. 现有 `metrics_registry`、日报代码和导出中文映射；
4. 无法确认业务含义的字段不进入白名单，不凭英文名猜测。

应用启动时仍从 `information_schema.columns` 一次读取真实类型，用于验证配置字段确实存在。数据库中未配置的新字段不会自动开放；配置存在而数据库缺失的字段记录启动错误并从运行目录排除。

数据字典确认的四张日报表共 189 个字段，两张 RRU 资产表共 38 个字段。字段说明进入策略目录，不再只依赖应用启动时临时读取数据库 comment。

## 确定性指标目录

计算指标使用代码注册，不执行 YAML 字符串公式。每个指标定义包含：

- 稳定指标 ID、中文名、别名和业务说明；
- 支持的 4G/5G 来源表和来源字段；
- 固定计算函数 ID；
- 单位、结果类型和适用粒度；
- 分母为零、空值和百分比字段的处理规则。

示例：

```yaml
nr_high_power_ratio:
  label: 5G高耗电小区设备占比
  description: 32通道和64通道小区占全部5G小区的比例
  source_table: nr_report_day_collect
  source_fields: [thirtytwo_channel_total, sixtyfour_channel_total, all_cell_total]
  calculator: nr_high_power_ratio
  unit: "%"
  grain: summary_day
```

日报代码中的确定性口径迁移到统一指标注册表，日报和数据自服务复用同一计算函数，避免同名指标出现不同算法。第一阶段覆盖当前日报已经使用的单位换算、可读率、高通道占比、低能效占比、共模站占比以及各类平均生效时长。

指标只作为查询输出项。规划器选中指标后，程序自动补齐来源字段，数据库返回基础行后再执行注册函数。指标定义和依赖随结果一起返回，主智能体不需要猜公式。

## 受控多表关系和结果粒度

结果粒度表示“一行结果代表什么”。默认按主表粒度返回；用户明确要求明细时才展开一条一对多关系。

第一批关系包括：

- 扩展结果与收缩结果：`cgi + stat_time`；
- 收缩结果与周边小区：`cgi + around_cgi`；
- 扩展结果与小时过程：`cgi + stat_time`；
- 扩展/收缩结果与休眠前负荷：`cgi` 加审核日期窗；
- 扩展/收缩结果与 5G 工参：`cgi` 加最新快照；
- 扩展/收缩结果与参数核查：`cgi` 加同日规则；
- 4G/5G 日明细与对应工参：`cgi + data_date`；
- 4G/5G 日明细与对应 RRU 资产：按 `cgi` 关联右表最新资产快照；同一小区可能包含多个 RRU，默认聚合资产字段，明确要求逐 RRU 时才展开资产记录。

一对多关系在默认粒度下先按审核键聚合，再与主表连接，避免小区数和指标被重复放大。同一请求只能展开一个明细轴，不能同时生成“每小时 × 每邻区 × 每 RRU”的笛卡尔积。

## 结构化查询计划

内部大模型不返回 SQL，只返回经过 Pydantic 校验的计划：

- `base_table`、`tables`、`relationships`；
- `select`：物理字段；
- `metrics`：已注册计算指标；
- `filters`、`group_by`、`aggregations`、`order_by`；
- `result_grain`、`limit`；
- `clarification`：存在歧义时给主智能体的澄清问题。

物理字段允许审核过的精确过滤、包含过滤、范围过滤和基础聚合。模型输出的未授权表、字段、指标、关系、第四张表、第二条明细轴或非法操作符必须在执行前拒绝。

## 无 Embedding 的候选召回

候选搜索只处理内存元数据：

1. 对问题、中文名、英文名和别名进行 Unicode NFKC、转小写和分隔符归一化；
2. 完整相等优先，连续包含次之；
3. 使用少量字符相似度处理错别字和英文变体；
4. 先取少量候选表、字段和指标，再把可达白名单关系交给规划器；
5. 候选不足、关系不可达或粒度不明确时返回澄清，不执行查询。

模糊匹配只影响候选召回，最终 SQL 标识符必须来自精确白名单。

## 返回契约

成功结果至少包含：

```json
{
  "success": true,
  "rows": [],
  "columns": [],
  "tables": [],
  "relationships": [],
  "metrics": [],
  "metric_definitions": [],
  "result_grain": "summary_day",
  "actual_date_range": {},
  "applied_defaults": [],
  "data_quality": {
    "complete": true,
    "missing_fields": []
  },
  "row_count": 0,
  "database_ms": 0,
  "download_url": null
}
```

`rows` 使用稳定中文列名；`columns` 同时保留字段或指标 ID、中文名、类型和单位。工具结果不包含诊断结论，不设置供 `DirectAnswerMiddleware` 直出的完整报告。主智能体根据结构化结果回答用户。

查询成功但零行仍返回 `success=true`，并说明实际条件和日期范围；它不等同于数据库异常。歧义返回 `clarification_required`，超时和执行异常返回脱敏的公开错误。

## 安全和性能

- 使用独立 `SELF_SERVICE_DATABASE_URL` 和只读 PostgreSQL 账号。
- SQL 由 SQLAlchemy Core 构造，值全部绑定参数。
- 每次查询使用只读事务和本地 `statement_timeout`。
- 默认最近 7 天，显式日期范围最大 90 天。
- 聊天最大 500 行，默认 50 行；Excel 最大 10,000 行。
- Schema、字段类型和关系目录只在启动时加载一次，请求期间不访问 `information_schema`。
- 单次请求只进行一次结构化规划调用和一条最终业务 SQL。
- 记录候选、计划、表、关系、粒度、字段、指标、各阶段耗时和行数，不记录密码或完整敏感参数。
- 目录预热失败不阻断已有专业工具。

## 验收标准

1. 每张授权表在策略文件中都有显式字段中文名和业务说明，数据库未登记字段不会自动开放。
2. 用户提供的数据字典中的六张表进入目录，其中两张 RRU 资产表可以单表查询，并可沿审核关系补充小区数据。
3. 扩展、收缩表字段继续使用此前 CSV 确认的中文名。
4. “查询衡阳最近七天 5G 节电率、业务量和平均深度休眠时长”返回物理字段与确定性计算指标，并附来源和单位。
5. 日报和数据自服务对同一指标调用同一个计算函数，结果一致。
6. “查询某小区扩展时段、需收缩时段和周边小区距离”可以沿两条审核关系查询三张表，默认不重复小区行。
7. 用户明确要求逐收缩记录、逐小时、逐参数项或逐 RRU 时只展开对应的一条明细轴。
8. 英文字段名、中文名、合理别名和轻微拼写变体可以召回候选；无可靠候选时要求澄清。
9. 工具返回结构化 `rows/columns/metrics/data_quality`，由主智能体完成比较和诊断，不直出分析报告。
10. 未授权表、字段、指标、关系和超范围查询在数据库执行前被拒绝。
11. 请求期间不查询 `information_schema`，执行 SQL 受只读、超时、日期和行数限制。
12. 单元、集成和全量回归测试全部通过，原有专业工具行为不变。
